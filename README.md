# MNIST digit recognizer — local server + drawing frontend

A convolutional network trained on MNIST, wrapped in a local FastAPI server with a
canvas frontend so the model can be tested on freshly drawn digits rather than only on
the held-out test set.

## About this project

The goal here is learning, not shipping a product. It's a practical application of the
NVIDIA *Getting Started with Deep Learning* course material — taking the concepts out of
the notebooks and building the whole thing end to end, including the parts a course
doesn't cover: how a trained model actually gets deployed, and how badly real input
differs from a clean dataset.

Specifically, it's practice with:

- **PyTorch** — defining an `nn.Module`, the training loop, `state_dict` save/load,
  `eval()` mode and `no_grad()` at inference
- **torchvision** — datasets, dataloaders, and the transform pipeline
- **NumPy** — array manipulation in the preprocessing path
- **pandas** — tabular handling of metrics and results
- **CNNs in particular**, as the groundwork for harder image recognition tasks later:
  convolution and pooling layers, feature maps, and why a CNN beats a dense network on
  image data

The uncomfortable lesson worth recording: a network can reach ~99% on the MNIST test set
and still perform noticeably worse on digits drawn by hand in a browser. MNIST digits are bounding-box cropped, scaled to a 20px long edge, and centered by center of mass. Matching that pipeline mattered more than anything about the model itself. See *What changed from the original preprocessing* below.

## Provenance

| Part | How it was built |
|---|---|
| `train.py`, `model.py` | Written by a human working alongside a coding agent. This is the part the project written my a human. Architecture, the training loop, and hyperparameters were made deliberately, with the agent used for review and assistance rather than authorship. |
| `static/` (HTML, CSS, JS) | Generated by a coding agent. The frontend is scaffolding for exercising the model, not a subject of study here. |
| `app.py`, `model_loader.py`, `preprocess.py`, `classify.py` | Generated by a coding agent, adapting the original hand-written inference script into a server. |

```
mnist-cnn/
├── train.py                 ← human + agent, the actual learning work
├── model.py                 ← human + agent, ConvNetwork definition
├── cnn_mnist_weights.pth    ← produced by train.py
│
├── app.py                   FastAPI server (routes, image intake)
├── classify.py              CLI, replaces the original classify.py
├── model_loader.py          loads ConvNetwork, runs inference
├── preprocess.py            canvas image → MNIST-shaped 28×28
├── requirements.txt
└── static/                  index.html, style.css, app.js  (agent-generated)
```

The serving files must sit in the same directory as `model.py` — `model_loader.py` does
`from model import ConvNetwork`, and the weights are meaningless without that class.

The original `classify.py` is superseded: model loading moved to
`model_loader.load_model()` (now run once at startup rather than per image),
`image_preprocessing()` moved to `preprocess.py`, and the softmax/argmax step moved to
`model_loader.predict_probs()`.

## Run

```bash
pip install -r requirements.txt
python app.py --port 8000
```

Open http://127.0.0.1:8000. Flags: `--host`, `--port`, `--model` (defaults to
`cnn_mnist_weights.pth`), `--device cpu|cuda`, `--reload`.

The server picks `cuda` when available, same as the original script. `--device cpu` is
useful for isolating a GPU issue from a preprocessing one.

## One thing to double-check

`NORMALIZE` at the top of `model_loader.py` is set to `False`, matching the original
inference script — `ToTensor()` gives `[0, 1]` and nothing further is applied.

If `train.py` applies `T.Normalize((0.1307,), (0.3081,))` and inference doesn't, that's a
live train/inference skew — fix it in both places and set `NORMALIZE = True` here. Worth
a look at the transform in `train.py`. A mismatch like this produces confident wrong
answers rather than obvious garbage, which is exactly why it survives casual testing.

## What changed from the original preprocessing

The original `image_preprocessing()` resized the whole frame to `(28, 28)` and inverted
unconditionally. Two consequences on canvas input:

- **`Resize((28,28))` squashes to a square** and preserves whatever margins the drawing
  happened to have. MNIST digits are cropped to their bounding box, scaled so the long edge is 20px with
  aspect ratio preserved, then placed in a 28×28 field centered on the digit's **center
  of mass** — not the center of its bounding box. `preprocess.py` reproduces that. This
  is usually the single biggest accuracy gap between test-set numbers and real drawings.
- **`1.0 - tensor` inverts unconditionally**, which is right for dark-ink-on-white but
  silently wrong for anything already white-on-black. `preprocess.py` reads the border
  pixels and inverts only when the background is light, so both work.

Everything downstream is identical to the original script: a `(1, 1, 28, 28)` float
tensor on the device, `torch.softmax(logits, dim=1)`, argmax for the label. Verified
numerically equal to the original inference path on the same input.

## Command line

`classify.py` calls the same two modules the server does, so its output always matches
the web UI:

```bash
python classify.py 21.jpeg
python classify.py samples/*.png --top 3 --save-processed
```

`--save-processed` writes the 28×28 the model actually saw as `NAME.processed.png`,
which is the fastest way to diagnose a wrong answer. Also takes `--model` and `--device`.
Exits non-zero if any image failed.

## API

```bash
curl -F "file=@21.jpeg" http://127.0.0.1:8000/predict
```

```json
{
  "prediction": 7,
  "confidence": 0.981,
  "probabilities": [0.001, "..."],
  "backend": "torch · cuda",
  "processed_png": "data:image/png;base64,..."
}
```

Also accepts `{"image": "data:image/png;base64,..."}` as JSON. `GET /health` reports the
device. Errors return JSON with a `detail` string: 422 blank image, 415 unreadable file,
413 over 5 MB.

## Debugging predictions

The `28×28 as sent` thumbnail in the UI is the exact array handed to `ConvNetwork`. When
a prediction looks wrong, check it first:

| What you see | Cause |
|---|---|
| Digit clipped at an edge | stroke ran off the canvas |
| Faint or broken strokes | `ctx.lineWidth` in `static/app.js` too thin for 28×28 |
| Black digit on white | polarity detection inverted — check the border of your input |
| Looks correct, label wrong | model or the `NORMALIZE` flag above, not preprocessing |

## Notes

- Stroke width is `ctx.lineWidth = 22` on a 336px canvas, which lands near MNIST's weight
  after the downscale. Thin lines nearly vanish at 28×28.
- Keyboard: Enter predicts, Escape clears.
- The grid guide is a CSS overlay above the canvas, so the bitmap sent to the server stays
  pure black ink on pure white. Don't move it into the canvas draw calls.
- Binds to `127.0.0.1`. Use `--host 0.0.0.0` only on a trusted network; no auth or rate
  limiting here.
